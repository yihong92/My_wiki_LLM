MCP 是什麼？
給 AI 一個通用插座

Model Context Protocol（模型上下文協定）入門：它解決什麼問題、怎麼運作、使用時要注意什麼。
約 15 分鐘 · 16 張首頁
先想一個問題

AI 很聰明，卻看不到你的資料

你問 AI

「幫我看一下上週 GitHub 上那個沒修好的 bug，順便在 Slack 跟組員說。」

AI 卡住了

它不在你的 GitHub 裡，也進不了你的 Slack。沒人幫它接線，它只能說「請把內容貼給我」。

模型能力進步得很快，但它們被關在資訊孤島外面；每接一個新資料來源，都得另外寫一套整合程式。

2 / 16要解決的問題
沒有標準的時候

每一對都要客製：M × N

3 × 4 = 12

3 個應用、4 個工具，就要寫 12 套整合。10 個應用、20 個工具，就是 200 套。

而且各家模型的工具格式都不一樣，換一家就要再改一次。

3 / 16要解決的問題：M×N
MCP 的解法

大家都接同一種插座：M + N

3 + 4 = 7

每個工具寫一次 MCP Server，每個應用做一次 MCP Client，彼此就能互通。

就像 USB-C：以前每台裝置一種接頭，現在一種接頭接全部。

4 / 16MCP 是什麼
一句話定義

MCP 是一個開放標準，
規定 AI 應用怎麼接外部資料與工具

MODEL

模型

會讀寫文字的 AI，例如 Claude。

CONTEXT

上下文

模型回答時能參考的資訊：檔案、資料庫、工具清單。

PROTOCOL

協定

雙方約好的溝通規則，像 HTTP 之於網頁。

由 Anthropic 在 2024 年 11 月開源。它只負責交換上下文，不會讓模型變聰明，也不規定應用怎麼使用模型。

5 / 16MCP 是什麼
怎麼運作 ①

三個角色：Host、Client、Server

  • Host：你在用的 AI 應用（Claude Desktop、VS Code）。
  • Client：Host 裡的連線員，一個 Client 只連一個 Server。
  • Server：提供資料或工具的程式，可以在本機，也可以在遠端。
6 / 16架構
怎麼運作 ②

Server 能提供三種東西

TOOLS

工具：去做事

可執行的函式，例如查資料庫、呼叫 API。

RESOURCES

資源：拿來讀

提供背景資料，例如檔案內容、資料表結構。

PROMPTS

提示範本

可重複使用的互動範本，例如示範怎麼用工具的例子。

例：一個資料庫 Server 可以同時給「查詢工具」＋「資料表結構資源」＋「查詢範例範本」。
每一種都能先用 list 問「你有哪些？」，所以清單可以隨時變動。

7 / 16原語
怎麼運作 ③

反過來，Server 也能請 Client 幫忙

SAMPLING

借用模型

Server 請 Host 的模型產生文字，自己不用綁定任何一家模型。

ELICITATION

問使用者

Server 請使用者補充資訊，或確認某個動作要不要做。

LOGGING

回報紀錄

Server 把日誌傳回 Client，方便除錯。

重點：MCP 是雙向的。工具、資料、範本放在同一個介面後面，這是它和「單純呼叫函式」最大的差別。

8 / 16原語（Client 端）
怎麼運作 ④

一次工具呼叫實際長這樣

  1. 問清單：Client 送 tools/list，Server 回傳工具名稱、說明、參數格式。
  2. 模型決定：使用者問天氣，模型選了 weather_current。
  3. 呼叫：Host 把請求轉給對的 Server。
  4. 拿結果：結果放回對話，模型再用它回答。
{
  "jsonrpc": "2.0", "id": 3,
  "method": "tools/call",
  "params": {
    "name": "weather_current",
    "arguments": {
      "location": "San Francisco"
    }
  }
}

訊息格式是 JSON-RPC 2.0：有 id 的是請求、要回覆；沒有 id 的是通知，例如「我的工具清單變了」。

9 / 16訊息流程
怎麼運作 ⑤

訊息走哪條路：本機或遠端

STDIO · 本機

同一台電腦

Host 直接啟動 Server 程式，用標準輸入／輸出傳訊息。
例：讀你電腦裡的檔案。

STREAMABLE HTTP · 遠端

透過網路

用 HTTP POST 傳訊息，一台 Server 可服務很多人。建議用 OAuth 做授權。
例：Sentry 官方 Server。

兩條路送的是同一種 JSON-RPC 訊息，所以寫 Server 的人不用為了換傳輸方式重寫邏輯。

10 / 16傳輸層
常見混淆

MCP 會取代 Function Calling 嗎？不會

FUNCTION CALLING

模型怎麼按按鈕

模型挑選工具、填好參數。各家模型格式不同，通常綁在一個應用裡。

MCP

按鈕的插頭長怎樣

規定應用怎麼找到、連上外部工具。底層仍然靠 function calling 執行。

只有一個應用、兩三個內部工具？直接用 function calling 就夠了。
要讓很多應用共用同一組工具時，才是 MCP 發揮的地方。

11 / 16MCP 與 Function Calling
發展歷程

兩年內，從一家公司的提案變成產業標準

2024-11Anthropic 開源 MCP，附 TypeScript／Python SDK 和 GitHub、Slack 等現成 Server。
2024–2025Zed、Replit、Sourcegraph 等開發工具陸續支援；之後加入遠端 Server。
2025-12捐給 Linux 基金會的 Agentic AI Foundation，由社群中立治理。
2026-07新規格改為「無狀態」：不用先握手，每個請求自帶版本資訊。

官方在 2026 年 7 月表示，主要 SDK 每月下載量接近 5 億次。注意：網路上很多 2025 年的教學還在講「先 initialize 握手」，那是舊版規格。

12 / 16發展歷程
使用前必知

能做事的 AI，被騙的代價也更大

間接提示注入

工具讀回的網頁、郵件裡藏指令，模型照著做。

工具投毒

惡意指令藏在工具的描述文字裡，模型本來就信任它。

中途變臉

Server 先正常，取得信任後更新成惡意版本。

三個好習慣：工具讀到的內容一律當成不可信 · 寫入、寄信、付款、刪除前要人工確認 · 只裝審查過的 Server 並固定版本。

13 / 16安全風險與防護
實務判斷

什麼時候該用 MCP？

適合用 MCP

  • 同一組工具要給好幾個 AI 應用用
  • 想直接用別人寫好的 Server（GitHub、Slack…）
  • 不想被綁在某一家模型廠商

可以先不用

  • 只有一個應用、一個模型、少數工具
  • 兩端程式都由你自己控制
  • 之後要共用時，再把函式包成 Server 即可
14 / 16MCP 與 Function Calling
小測驗

檢查一下你懂了沒

1. VS Code 同時連了 3 個 MCP Server，它裡面有幾個 MCP Client？
3 個。一個 Client 只對應一個 Server。
2. 想讓 AI 讀取資料表結構，比較適合用哪一種原語？
Resources。它是拿來讀的背景資料；要執行查詢才用 Tools。
3. 有了 MCP，是不是就不需要 function calling？
不是。MCP 底層還是靠 function calling 讓模型選工具；MCP 負責統一「怎麼接」。
15 / 16名詞表
重點回顧

帶走這五句話

  1. MCP 是連接 AI 應用與外部資料、工具的開放標準。
  2. 它把 M×N 套客製整合變成 M+N。
  3. 角色：Host 裡有多個 Client，每個 Client 連一個 Server。
  4. Server 提供 Tools／Resources／Prompts；訊息走本機 stdio 或遠端 HTTP。
  5. 它不取代 function calling，而且安全要靠使用方式。
